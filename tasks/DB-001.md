## :white_check_mark: Task Breakdown (실행 계획)
- [ ] **`PRAGMA user_version` 기반 마이그레이션 러너 구현** (`migrations/vNNN_*.sql` 순차 적용, 버전당 단일 트랜잭션). Alembic·Prisma·SQLAlchemy 미사용 (`DEC-05`)
- [ ] DB 스키마 정의 — **8개 테이블**: `Workspace_Meta`, `File_Meta`, `Wiki_Content`, `Rename_History`, `Analytics_Log`, `Watcher_Config`, `App_Config`, `Async_Task`
- [ ] 초기 마이그레이션 `migrations/v001_initial_schema.sql` 작성 및 적용
- [ ] **`DatabaseManager` 구현** — 스레드-로컬 커넥션(`threading.local`), `sqlite3.Row` factory, `transaction()` 컨텍스트 매니저(`isolation_level=None` + 명시적 `BEGIN`)
- [ ] **커넥션 생성 시 PRAGMA 일괄 적용**: `journal_mode=WAL`, `foreign_keys=ON`(커넥션 단위 필수), `busy_timeout=5000`, `synchronous=NORMAL`
- [ ] `Async_Task` 인덱스 생성: `(status)`, `(workspace_id, task_type)`
- [ ] **`File_Meta` 경로 컬럼 2개 분리** (`DEC-08`): `current_path`(NOT NULL, `UNIQUE(workspace_id, current_path)`) / `original_path`(NOT NULL, 불변). `UNIQUE` 제약은 `current_path`에만 적용한다
- [ ] `File_Meta(current_path)` 인덱스 생성 — Watcher가 `src_path`로 행을 역조회하는 경로다 (`DEC-08`)
- [ ] **`File_Meta`에 `vector_ids` 컬럼을 만들지 않는다** (`DEC-09` 폐기 결정). 벡터 SSOT는 Chroma 단독이다
- [ ] **`workspace_id` FK 전부에 `ON DELETE CASCADE` 지정** (`File_Meta`, `Wiki_Content`, `Rename_History`, `Analytics_Log`, `Watcher_Config`, `Async_Task`) — `DEC-09`
- [ ] **저장 타입 규약 적용 (`DEC-11`)**: 모든 UUID는 `TEXT`(하이픈 36자 소문자), 모든 DATETIME은 `TEXT` ISO-8601 **UTC**(`YYYY-MM-DDTHH:MM:SS.ffffffZ`). UUID를 BLOB로, 시각을 INTEGER epoch로 저장하지 않는다 (예외: `last_modified`는 OS epoch이므로 `REAL` 유지)
- [ ] **타임스탬프 DEFAULT를 `(strftime('%Y-%m-%dT%H:%M:%fZ','now'))` 로 통일** — `DEFAULT CURRENT_TIMESTAMP`는 `Z`·소수점이 없는 다른 포맷을 만들어 규약을 깨뜨린다 (`DEC-11`)
- [ ] **`ON UPDATE CURRENT_TIMESTAMP`를 스키마에 쓰지 않는다** (SQLite 미지원 MySQL 문법). `updated_at`은 각 Repository의 `UPDATE` 문에서 명시 대입하며, **`AFTER UPDATE` 트리거를 만들지 않는다** (`DEC-11`)

## :test_tube: Acceptance Criteria (BDD/GWT)
Scenario 1: 스키마 초기화 및 생성
- Given: 데이터베이스 파일이 존재하지 않는 빈 환경이 주어짐
- When: 마이그레이션 실행 명령어를 호출함
- Then: `%LocalAppData%\CorpBrain\corpbrain_meta.db` 물리 파일이 생성되고, 명세된 **8개**의 테이블이 누락 없이 생성된다.

Scenario 3: 좌초 Task 복구 전이 (DEC-04)
- Given: `Async_Task`에 `status='running'` 레코드가 남은 상태로 앱이 비정상 종료됨
- When: 앱을 재시작하여 부팅 복구 절차를 실행함
- Then: 해당 레코드가 `interrupted`로 전이되고, 자동 재개 없이 사용자 확인 대기 상태가 된다.

Scenario 5: `updated_at` 갱신 검증 (DEC-11)
- Given: `Wiki_Content` 행이 INSERT되어 `updated_at` 기본값이 채워진 상태
- When: Repository를 통해 해당 행의 `markdown_content`를 UPDATE함
- Then: `updated_at`이 새 UTC ISO-8601 값(`...Z`)으로 갱신된다. (트리거 없이 `UPDATE` 문의 명시 대입으로 동작함을 확인)

Scenario 4: 워크스페이스 삭제 CASCADE 검증 (DEC-09)
- Given: `File_Meta`·`Wiki_Content`·`Analytics_Log` 자식 행이 존재하는 워크스페이스가 주어짐
- When: `Workspace_Meta` 행을 삭제함 (`PRAGMA foreign_keys=ON` 상태)
- Then: 모든 자식 행이 함께 제거되고 고아 행이 남지 않는다.

Scenario 2: DB 커넥션 및 쿼리 동작 검증
- Given: 정상적으로 초기화된 데이터베이스가 주어짐
- When: Workspace 테이블에 임의의 더미 데이터를 INSERT 한 후 SELECT 함
- Then: 삽입한 데이터가 정확하게 조회되며, 에러 없이 커넥션이 종료된다.

## :gear: Technical & Non-Functional Constraints
- 성능: 쿼리 실행 시간 p95 ≤ 10ms (단순 CRUD 기준)
- 안정성: 멀티스레드 환경 대비 WAL 모드 필수. **커넥션 풀 라이브러리 대신 스레드-로컬 커넥션**을 사용한다 (`sqlite3` 커넥션은 스레드 간 공유 불가)
- 데이터 무결성: 외래키 제약은 **DB 단위가 아닌 커넥션 단위**로 적용되므로, 모든 신규 커넥션에서 `PRAGMA foreign_keys = ON`을 반드시 재실행해야 한다
- 쓰기 직렬화: SQLite는 writer가 1개다. 쓰기 트랜잭션 내부에서 LLM 추론·파일 I/O 등 장시간 작업을 수행하지 않는다 (`DEC-05`)
