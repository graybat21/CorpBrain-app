# SCAN-CMD-01 성능 기준선 (INF-TEST-01 / 이슈 #25)

> **관련 요구사항**: REQ-NF-001 (UI Freezing 방지), TC-PERF-001
> **측정 도구**: `scripts/bench_scan.py`
> **CI 통합 여부**: **하지 않음** — 사유는 §4

---

## 1. 실행 방법

```bash
python scripts/bench_scan.py                        # 기본: 1,000개 x 10회
python scripts/bench_scan.py --files 5000 --runs 3
python scripts/bench_scan.py --budget-ms 5000
```

종료 코드는 p95 가 예산을 초과하면 `1`, 충족하면 `0` 이다. 하드웨어가 고정된 셀프호스트 러너나 릴리스 체크리스트에는 붙일 수 있다.

측정 대상은 **트리 순회 + `File_Meta` insert** 다. 파일 본문은 한 줄이므로 디스크 읽기 대역폭은 측정하지 않는다 — REQ-NF-001 이 문제 삼는 구간이 아니다.

## 2. 기준선 (2026-08-10 최초 측정)

| 항목 | 값 |
|---|---|
| OS | macOS 26.5.2 (arm64) |
| CPU | Apple Silicon (arm64) |
| Python | 3.10.20 |
| 저장장치 | 내장 NVMe SSD |

### 1,000개 파일 (AC S1 기준 규모, 10회)

| 지표 | 값 |
|---|---|
| min | 13.4 ms |
| median | 13.8 ms |
| **p95** | **15.4 ms** |
| max | 15.4 ms |
| 파일당 | 0.014 ms |
| 예산 (REQ-NF-001) | 5,000 ms |
| **여유** | **약 325배** |

### 5,000개 파일 (3회)

| 지표 | 값 |
|---|---|
| median | 78.6 ms |
| p95 | 94.7 ms |
| 파일당 | 0.016 ms |

**선형성 확인**: 1,000개 → 5,000개에서 파일당 비용이 0.014 ms → 0.016 ms 로 거의 변하지 않는다. 스캔 비용은 파일 수에 선형이다.

## 3. 회귀 판정 기준

절대 시간이 아니라 **이 문서의 기준선 대비 비율**로 판단한다. 다른 하드웨어의 절대값은 비교 대상이 아니다.

| 상태 | 파일당 비용 (1,000개 기준) | 조치 |
|---|---|---|
| 정상 | < 0.05 ms | 없음 |
| 주의 | 0.05 ~ 0.5 ms | 원인 확인, 이 문서에 기록 |
| 회귀 | > 0.5 ms (기준선의 35배 이상) | 이슈 등록 후 원인 수정 |

예산 5,000 ms 는 회귀 감지에 사실상 무의미하다 — 325배 여유가 있으므로, 성능이 100배 나빠져도 예산은 통과한다. **그래서 예산 대신 기준선을 쓴다.**

## 4. CI 게이트로 만들지 않은 이유 (AC 와의 차이)

이슈 #25 AC S2 는 "p95 가 5,000ms 를 초과하면 테스트가 Fail" 을 CI 에 통합하도록 요구한다. 이 부분은 **의도적으로 다르게 구현했다.**

**1) 공유 러너의 디스크 성능 분산이 측정 마진보다 크다.** GitHub 공유 러너는 실행마다 다른 물리 머신에 배정되고, I/O 이웃 부하도 제어할 수 없다. 같은 커밋이 머신에 따라 통과/실패하는 게이트는 "실패하면 재실행" 습관을 만들고, 그러면 **진짜 회귀도 재실행으로 초록색이 된다.** 게이트가 없는 것보다 나쁘다. 이 문제는 이미 이슈 #110 (CI flake) 으로 한 번 겪었다.

**2) 5,000 ms 예산은 이 코드에서 회귀를 감지하지 못한다.** 실측 p95 가 15.4 ms 이므로 여유가 325배다. 성능이 100배 나빠져도 게이트는 통과한다. 즉 AC 문구 그대로 구현해도 **회귀 감지라는 목적을 달성하지 못한다** — 통과하는 게이트를 CI 에 추가하는 것에 그친다.

**3) CI 가 재현 가능하게 검증할 수 있는 부분은 별도로 자동화했다.** `tests/test_issue_25.py` 9건이 매 CI 실행에서 돌아간다:

| 검증 | 무엇을 잡는가 |
|---|---|
| 1,000개 전량 insert | 빠르지만 파일을 누락하는 스캔 |
| 확장자 4종 비율 유지 | 특정 포맷만 누락하는 필터 버그 |
| 10K 가드 미발동 | 상수 오류로 정상 규모가 절단되는 것 |
| **복잡도 비율** (4배 파일 → 8배 미만) | 복잡도 클래스 변화 (2차식 변이 실측 15.5배) |
| **`bulk_upsert` 호출 1회** | N+1 상수배 폭증 |
| 재스캔 시 행 중복 없음 | 실행마다 파일 수가 늘어나는 결함 |
| 벤치마크 스크립트 동작 + FAIL 경로 | 아무도 실행할 수 없는 벤치마크 |
| `bench_scan` 이 ci.yml 에 없음 | 이 결정의 조용한 되돌림 |

**두 성능 테스트는 서로를 대체하지 않는다.** 뮤테이션으로 확인한 사실:

- `bulk_upsert` 를 파일당 1회로 쪼갠 N+1 변이 → 비율 **4.39배** (선형, 비율 테스트 **통과**), 총 52 ms (예산 **통과**). 호출 횟수 테스트만 잡았다.
- 누적 리스트를 매 파일 재기록하는 2차식 변이 → 비율 **15.5배** (비율 테스트 **실패**).

즉 비율 테스트는 복잡도 변화만, 호출 횟수 테스트는 상수배 폭증만 잡는다. 둘 다 필요하다.

**한계 명시**: 이 구성은 벽시계 성능 회귀를 매 커밋마다 자동 감지하지 못한다. 절대 성능 확인은 릴리스 전 이 스크립트를 수동 실행하고 아래 이력에 남기는 방식으로 담보한다.
